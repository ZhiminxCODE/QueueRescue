# Security and infrastructure review

Reviewed 2026-11-16 against the prepared development stack and local simulator. This is a source review with automated offline checks, not a penetration test or evidence of a deployed AWS security posture. No resources were deployed, real queues inspected or account permissions changed.

AWS documents [required versus optional MFA and first-sign-in exceptions](https://docs.aws.amazon.com/cognito/latest/developerguide/user-pool-settings-mfa.html). Complete enrollment and verify a later MFA challenge; the initial enrollment session alone is insufficient evidence. DynamoDB documents [partition-key IAM conditions](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/specifying-conditions.html). These changes require a reviewed apply for any existing stack.

## Reviewed boundaries

- **Identity and role escalation:** API Gateway requires the configured issuer/client and API scope. Lambda accepts access tokens through the authorizer context and enforces group capabilities independently. Request bodies, role headers and browser claims cannot grant permissions. OAuth uses state-bound PKCE and a short-lived access token; ID/refresh tokens are discarded. Recovery approval is bound to the immutable plan hash and a different authenticated subject. Group administrators remain privileged; assigning both capability groups requires governance outside this app. See AWS's [JWT authorizer validation contract](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-jwt-authorizer.html).
- **IAM and queue access:** function roles contain no IAM, PassRole or role-assumption grants. Collector may receive/release visibility only on the configured inspection DLQ, with no DeleteMessage permission. API reads its attributes; replay sends only to the replay queue; consumer receives/deletes only source/replay messages. Each role writes only its own function log group. Workflow invokes only replay. API evidence lookup reads only the configured consumer/replay log groups, without Unmask or Logs Insights access. API and replay still share broad write access within this stack's recovery ledger because they implement its control protocol; this is a workspace boundary, not multi-tenant isolation.
- **Snapshots and masking:** evidence bucket blocks public access, enforces TLS, encrypts and versions objects. Snapshot writes are conditional; evidence checksums are bound to ledger records. API payload masking covers nested sensitive keys, email-like values and long numbers; malformed payloads are withheld. This is heuristic redaction, not a DLP guarantee. Unknown sensitive fields and operation identifiers may remain visible to authorized readers. Raw snapshots are deliberately retained in private S3 and accessible to principals with direct bucket access. Use synthetic data for the demo.
- **Recovery safety:** transactional reservations, one-use approvals, persisted request identities and conservative uncertain-send handling remain covered by safety tests. SDK retries do not repeat possibly accepted sends; orchestration avoids automatic send-task retries. Business verification, rather than transport success, establishes recovery. The collector never deletes originals; receiving does change visibility.
- **Retention and audit:** queue retention and snapshot access deadlines remain separate. Only ledger snapshots/control records carry TTL; business idempotency and audit tables do not inherit it. Versioned evidence lifecycle expires current objects after seven days and noncurrent versions after one day. Physical deletion is asynchronous. Deletion protection and disabled force-destroy guard accidental destruction; application audit appends are not WORM protection against account administrators. CloudTrail coverage/protected audit retention remains an open checklist item.
- **Local hosting:** simulator binds loopback, validates Host and mutation Origin, limits JSON bodies, checks static paths and offers explicit demo personas. Those personas are a simulation feature and are unsuitable as a hosted authentication system. Production frontend hosting is still unimplemented. The static server's CSP applies to built assets, not Vite development hosting. A successful XSS could still read sessionStorage tokens; the prototype has no HttpOnly BFF session service.
- **Cost and deployment:** fresh minimal defaults keep consumer mappings disabled and consumer/replay concurrency zero. Budget alerts are warnings, not caps. Account plan, credits, shared allowances, deployment permissions, concurrency quota and explicit cost review remain unresolved deployment gates. No zero-bill guarantee is made. Standard profile uses a shared stack KMS key and broader cryptographic operations within that key; per-service key separation is future hardening.

## Dependency and verification results

- `npm audit --json`: zero reported advisories across 51 installed dependency entries, including development/optional dependencies.
- [OSV querybatch](https://google.github.io/osv.dev/api/) against the 23 distinct pinned PyPI runtime/test package versions: no reported advisories. `pip check`: no broken requirements. These are dated advisory snapshots, not proof that dependencies have no vulnerabilities; rerun before deployment.
- Full Python safety/HTTP/offline AWS suite passed (169 tests at the review checkpoint); an additional HTTP CSP/privacy-header test and the static-policy test passed after the final header change.
- Frontend: 26 tests passed; local production build and a separate AWS-mode build using synthetic public endpoints passed. The emitted connection manifests matched each mode. Existing lucide directive warnings are nonblocking.
- Terraform formatting and schema validation passed; all 12 mocked-provider plans passed. Lambda packaging from pinned requirements passed. Mocking does not establish real IAM authorization, account quota, service behavior or billing.

Raw scan/test/build output stays in ignored `.data/`; dependencies and Lambda/frontend build artifacts are excluded from Git. Reproduce with the commands in the README and `terraform -chdir=infra/aws test` using the pinned tool/provider. Never run apply as a substitute for offline validation.
